WHAT ONEBUSAWAY ACTUALLY IS (verified, not vibes)
--------------------------------------------------------------------------------

  github.com/OneBusAway: onebusaway-application-modules (server),
  onebusaway-api-webapp (REST), onebusaway-gtfs-modules (GTFS lib),
  onebusaway-docker (official Docker compose), Wayfinder (SvelteKit web UI),
  iOS/Android apps, OBACloud sidecar (push alarms, Live Activities).
- REST API surface (full list from developer.onebusaway.org + official
  OpenAPI spec at OneBusAway/sdk-config/stainless/openapi.yml):
    arrivals-and-departures-for-stop/{id}
    arrivals-and-departures-for-location   <- one call, radius/bbox, every
                                              predicted arrival nearby
    stops-for-location / routes-for-location / stops-for-route
    trip-details/{tripId}                  <- status: live position, bearing,
                                              scheduleDeviation (sec), nextStop,
                                              predicted flag, occupancyStatus/
                                              Count/Capacity (CROWDING),
                                              nextTripId/previousTripId
                                              (bus continues as another route)
    trips-for-location / trips-for-route / vehicles-for-agency
    schedule-for-stop / schedule-for-route (full-day timetables)
    shape/{shapeId}, search/route, search/stop, agencies-with-coverage
- Official TypeScript SDK on npm: onebusaway-sdk@1.21.1 (Stainless-generated).
- CORS verified open (Access-Control-Allow-Origin: * on api.pugetsound...).
  key=TEST works but is shared/rate-limited; real use needs a free key per
  region or your own deployment.

================================================================================
PLAY A — HOSTED OBA IN COVERED REGIONS (cheap, partial)
================================================================================
What it changes: TimeTransit becomes a provider-dispatch app. A small
"who covers this origin?" check routes live-ETA calls to OBA instead of the
Transit API when inside an OBA region.

Effects:
+ Live ETAs, nearby departures, route cards, live bus marker in Seattle,
  Tampa, DC, San Diego, Davis, Adelaide — with no per-call Transit quota.
+ San Diego is adjacent to TimeTransit's turf: OC->SD trips (Metrolink to
  Oceanside + Coaster) could have live legs on BOTH ends.
+ arrivals-and-departures-for-location collapses today's 2-call
  nearby_stops -> stop_departures pattern into ONE call — cheaper + fresher
  for the Nearby Now strip, tap cards, and saved-places board.
+ schedule-for-stop gives real departure boards in OBA regions WITHOUT
  building a GTFS index (scan.ts needs a per-agency index; OBA doesn't).
- Needs a free API key per region; TEST is shared + throttled (hit a 429).
- Keys live in the worker relay if we don't want them in the bundle — CORS
  is open so direct calls work, but a bundled key is quota-theft bait.
- MTA NY is SIRI-only — skip unless we ever write a SIRI client.
- Does nothing for LA/OC. This alone is not "drastic" for home turf.

Effort: small-medium. It's a provider abstraction over transit.ts's
functions (liveDepartures / departuresNear / routeInfoAt / liveVehicle)
plus a regions bounds check (ship ~200 lines of the v3 regions JSON).

================================================================================
PLAY B — SELF-HOSTED OBA FOR SOUTHERN CALIFORNIA (the drastic one)
================================================================================
The idea: run our own OBA server, feed it:
  - OCTA GTFS (octa.net/current/google_transit.zip — we already consume it)
  - OCTA GTFS-RT tripupdates + vehiclepositions + servicealerts (keyless,
    api.octa.net — already relayed at /gtfsrt/*)
  - LA Metro GTFS (gitlab.com/LACMTA/gtfs_{bus,rail} — keyless, already used
    for the network layer)
  - LA Metro GTFS-RT via Swiftly (api.goswift.ly — free key, Authorization
    header; OBA supports per-feed auth headers via FEED_API_KEY/
    FEED_API_VALUE). NOTE probed 11-12: api.metro.net is a keyless JSON API
    (route_overview verified, 124 routes) but its real-time trip_detail
    endpoints returned [] — likely needs an OAuth account or has other
    gating — and sends NO CORS headers (relay required regardless). It also
    has a WebSocket pushing vehicle_positions/trip_updates every 3 s —
    interesting alt path, auth status unverified. For OBA ingestion,
    Swiftly's GTFS-RT protobuf is the reliable path.

Official path exists: github.com/OneBusAway/docker — `oba_bundler` builds a
bundle from GTFS_URL, `oba_app` serves api-webapp. Needs a JVM container +
MySQL/Postgres (JDBC_*). Render.com deploy guide exists; OBACloud (managed
hosting by Open Transit Software Foundation — Tampa & Davis run on it) is
the "ask someone else to run it" option.

What it buys, mapped to features:

1. KILL THE QUOTA CEILING. The whole live layer is currently rationed:
   Transit free tier = 5 calls/min + 1,500 calls/month, hard suspension,
   revocable at will, "Powered by Transit" badge required, no archiving.
   Self-hosted OBA = our server, our rules, effectively unlimited calls.
   Every throttled feature becomes always-on: per-leg ETAs, the 60 s
   alternative-comparison cap, board ETAs, Nearby Now, tap cards.
   This is the single biggest effect — it converts live ETA from a demo
   feature into a core feature.

2. A REAL PREDICTION ENGINE instead of raw delay passthrough. Today
   gtfsrt.ts applies raw feed delays to the scan. OBA blends schedule +
   vehicle positions + layovers + frequency-based trips into per-stop
   predicted arrival/departure times — that's what trip-details'
   `predicted`/`scheduleDeviation` actually is. Better ETAs, better
   watchdog re-checks, better transfer-miss detection.

3. LA METRO JOINS THE REALTIME WORLD. Metro legs currently fall back to
   the capped Transit API for live vehicles (see liveVehicle comment in
   transit.ts). Self-hosted OBA ingests Metro GTFS-RT -> Metro buses AND
   rail get predicted ETAs + live positions + alerts, same as OCTA.

4. ONE CALL FOR NEARBY DEPARTURES. arrivals-and-departures-for-location
   (radius query) serves Nearby Now, tap cards, and the saved-places
   board — replaces N stop lookups + batched departures. The worker
   /api/nearby and /api/board routes get simpler too.

5. LIVE VEHICLE LAYER. vehicles-for-agency + trips-for-location give every
   active bus position + bearing — could paint a real "buses around me"
   layer, not just the one bus on a selected leg.

6. NEW UX SURFACES no current source offers:
   - Occupancy: trip-details occupancyStatus/Count/Capacity -> "crowded"
     badges (IF the OCTA/Metro feeds carry occupancy — unverified).
   - Block chaining: nextTripId/previousTripId -> "stay seated, this bus
     becomes the 57" and smarter watchdog (vehicle persists across tripId).
   - nextStop/closestStop + scheduleDeviation per leg -> richer riding
     view ("2 stops away, running 4 late").

7. RELIABILITY MODEL GOES WIDE. Self-hosted OBA data isn't under Transit's
   no-archiving terms. Poll trip-details/arrivals -> predicted-vs-actual
   observations at scale -> statistics converge faster. Moonshot version:
   the onebusaway-gtfs-realtime-archiver module (or a cron) builds a
   historical delay dataset -> bake "typically +4 min at this stop at 5pm"
   into journey-time ranking itself.

8. GTFS-RT RE-EXPORT (lowest-diff variant). OBA can re-export combined
   GTFS-RT (trip updates/positions/alerts). A self-hosted OBA could act as
   a SoCal RT NORMALIZER: OCTA + Metro in, one unified GTFS-RT out — which
   the EXISTING gtfsrt.ts decoder consumes unchanged. Client diff ≈ zero.
   (Verify the exporter webapp ships in the Docker image first.)

Costs/risks, honestly:
- Breaks the "no backend" purity: adds a JVM + relational DB to infra
  (worker stays serverless; this can't be).
- Multi-agency: `GTFS_RT_FEEDS` env (verified in OneBusAway/docker README)
  takes a JSON array of feeds {tripUpdatesUrl, vehiclePositionsUrl,
  alertsUrl, refreshInterval, agencyIds[]} — OCTA + Metro realtime in ONE
  deployment via a single env var. RESIDUAL: static side is still one
  GTFS_URL per bundle — combining OCTA+Metro+MetroRail static GTFS needs
  either a merged zip (gtfstidy/merge tool — the image ships gtfstidy
  already) or multi-input bundle build. Verify in the spike; OCTA-only is
  a fine v1 anyway since that's Dave's turf.
- You become the data pipeline: feed outages, GTFS version drift, bundle
  rebuilds on schedule changes.
- OBA needs BOTH tripUpdates + vehiclePositions for positions (their docs).

ACCURACY SCOREBOARD (Dave's idea, 11-12)
--------------------------------------------------------------------------------
Goal: log predicted times vs real-ride outcomes, then compare providers
(OBA vs raw GTFS-RT vs Transit API) in a table with accuracy rates.

Verdicts:
- External DB for OBA itself: NO. Its DB is rebuildable scratch from the
  bundle; a hosted DB adds latency + a sleeping free-tier dependency and
  stores nothing valuable. In-compose Postgres on A1 stays.
- Log store for OUR accuracy data: YES — but the best "free provider" is
  one already owned: the Cloudflare Worker. D1 free tier (5GB, 100k
  writes/day) or the existing TT_STATE_KV. Zero new accounts, rides the
  existing /api/* route pattern. Accuracy log is OUR data (not OBA's) so
  it belongs on OUR infra anyway — survives VM rebuilds/migrations.

Why this is cheap: the bones already exist.
  - reliability.ts/reliabilityStore.ts = a complete observation model
    (observation, mergeObservations, weighted statistics, GPS-vs-feed
    weighting, 10k cap, simulated-data quarantine — the ?simulate=1 lab
    can't pollute real stats).
  - boarding.ts + useTripTracking = real-ride ground truth (actual
    board/arrive times from GPS).
  - ReliabilityPanel.tsx = existing UI shell for these stats.
  New work, three pieces:
    1. Tag predictions with source: {route, stop, scheduled, predicted,
       provider: octa-rt|oba|transit, queriedAt}.
    2. Close the loop: boarding detection actuals paired to predictions.
    3. Table per provider: mean error, % within +/-3min, bias, n.
  Payoff: "does OBA beat raw delay?" becomes a measured scoreboard over
  weeks of real rides, not a one-afternoon vibe check — and any future
  provider is just another column. Honest limit: ground truth = Dave's
  rides only — which matches the stated ship criterion exactly.

WHAT OBA DOES *NOT* DO (scope honesty)
--------------------------------------------------------------------------------
- No trip planning. OBA pairs with OTP; MOTIS/Transitous + our scan stay.
- No geocoding/POIs. Photon/TomTom/Overture stay.
- Doesn't change journey-time ranking directly — all its value is in the
  realtime layer (ETAs, positions, alerts, occupancy).
- Hosted regions won't help LA/OC. Self-host is the only OBA play that
  touches home turf.

THE HONEST ALTERNATIVE (the "do we even need OBA" question)
--------------------------------------------------------------------------------
We could get ~70% of Play B's benefit by extending gtfsrt.ts: relay
/gtfsrt/metro/* to api.metro.net or Swiftly (key stays worker-side), decode
with the existing protobuf decoder, feed scan + watchdog + a vehicle layer.
What self-hosted OBA adds beyond that: correct trip-matching across
agencies, real per-stop prediction (vs raw delay), schedule-for-* boards,
occupancy, block info — a prediction engine vs a passthrough.
Decision axis: ops appetite + money vs correctness and feature ceiling.

REVISED RECOMMENDATION (after Dave's constraints)
--------------------------------------------------------------------------------
Ordered by value-per-effort, OC-safe all the way down:

  STEP 1 (cheap, OC-first): extend gtfsrt.ts + relay for LA Metro GTFS-RT

    Zero effect on OCTA behavior; pure addition. ~90% of "Metro joins

  STEP 2 (spike): OBA Docker locally with the OCTA bundle. Judge whether
    OBA's predicted arrivals visibly beat raw delay passthrough on a known
    route (e.g. 55 on Haster). This is the go/no-go evidence for Play B.
  STEP 3 (if spike convinces): self-host SoCal OBA -> becomes THE live
    provider for home turf; Transit API demoted to fallback for elsewhere.
    Solves quota AND the release-scaling problem in one move.
  STEP 4 (free rider): once a LiveProvider interface exists, region
    dispatch to hosted OBA (Seattle/Tampa/DC/SD/Davis) is nearly free —
    and explicitly expansion-safe: dispatch defaults to current behavior
    outside OBA bounds, so OC is untouched.
